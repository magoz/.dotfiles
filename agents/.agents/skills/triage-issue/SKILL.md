# Triage Issue

Move one GitHub issue from a report to an evidence-backed next state.

This is an explicitly invoked workflow:

```text
/skill:triage-issue <issue-number-or-url>
```

## Initial scope

This first version:

- supports GitHub Issues through `gh`;
- runs from a local clone of the issue's repository;
- handles one issue per invocation;
- uses fresh, read-only investigation agents when useful;
- allows only issue comments and label transitions on GitHub;
- does not decompose large work yet.

## Hard boundaries

Never:

- fix or implement the issue;
- edit project/source files;
- create a branch or worktree;
- assign the issue;
- commit, push, open a pull request, or merge;
- run destructive database, migration, production, or external-side-effect commands;
- let an investigator mutate GitHub;
- invent product, domain, architecture, security, or scope decisions.

The parent Pi session is the sole GitHub mutator. Investigators return evidence to the parent.

## State vocabulary

Category and state are separate.

Category labels:

- `bug`
- `enhancement`

Workflow state labels:

- `needs-triage`
- `needs-info`
- `needs-decision`
- `ready-to-implement`
- `wontfix`

An issue should have at most one workflow state label. Native dependencies remain separate from readiness: a sufficiently specified issue may be `ready-to-implement` while still blocked by another issue; execution workflows must check blockers.

This skill does not create labels. During preflight:

- if required labels are missing, show the exact missing labels and stop with an actionable setup blocker;
- do not begin triage while the state vocabulary is incomplete.

## Comment provenance

Every GitHub comment created by this workflow starts with:

```markdown
> *Generated by an AI agent during issue triage.*
```

Post consolidated evidence and conclusions. Do not paste raw subagent transcripts, secrets, environment values, or irrelevant command output.

## Process

### 1. Resolve the issue and repository

- Require an issue number or GitHub issue URL.
- Confirm the current working directory is a local clone of the issue's repository.
- If it is not, stop and request the correct local repository path; do not guess, clone, or inspect another checkout.
- Confirm the target is an issue rather than a pull request.
- Read the full issue body, comments, labels, assignees, author, dates, and available dependency/sub-issue information.
- Read prior triage comments and the newest `## Agent Brief`, if any. Do not repeat resolved questions.

### 2. Preflight state

- Verify the workflow labels exist.
- Detect conflicting workflow state labels. Do not silently choose between conflicting states.
- If the issue is untriaged, normalize it to `needs-triage` before investigation.
- Preserve unrelated labels and metadata.
- If the issue is already closed, assigned, or linked to active implementation, report that state and stop unless the user explicitly asked for re-triage.

### 3. Gather repository context

Read before investigating:

- root repository guidance such as `AGENTS.md` or `CLAUDE.md`;
- the nearest nested owner guidance for the affected area;
- relevant project patterns, ADRs, and durable domain documentation that already exist;
- existing tests and analogous implementations near the reported behavior.

Do not impose `CONTEXT.md`, ADR, or tracker scaffolding on repositories that use another knowledge hierarchy.

Check:

- whether the requested behavior already exists;
- whether the issue duplicates another open or closed issue;
- whether repository rules or prior decisions contradict the request;
- what observable seam could verify the report and later protect the behavior.

### 4. Investigate read-only

Use a fresh, read-only exploration agent when it materially improves independence or context isolation. Give it:

- the issue URL/number and full report;
- the local repository path;
- the exact evidence questions;
- project guidance to consult;
- explicit instructions not to edit files, mutate GitHub, assign work, or implement a fix.

The investigator should return:

- whether the reported claim was confirmed, disproved, or remains unverified;
- reproduction command or user flow, when safe and available;
- relevant code path and analogous behavior;
- likely change boundary without prescribing a solution prematurely;
- a proposed behavioral validation seam;
- missing reporter facts;
- unresolved human-owned decisions;
- confidence and residual uncertainty.

The parent may investigate directly for trivial issues. Do not launch a subagent merely to satisfy the workflow.

### 5. Use proportionate evidence

Evidence depth follows uncertainty.

For an obvious mechanical defect, direct code evidence plus an established correct analogue may be enough to establish the current behavior and likely boundary.

For uncertain, intermittent, environment-specific, or high-risk bugs, require a tighter diagnosis loop before readiness. Prefer a safe, deterministic, agent-runnable signal that can detect the reported symptom.

Do not claim runtime reproduction when only static inspection was performed. State exactly what was and was not verified.

If safe reproduction requires credentials, production access, destructive state, external side effects, or unavailable infrastructure, do not improvise. Route to `needs-info` or `needs-decision` with one actionable request.

### 6. Choose one outcome

#### `needs-info`

Use when a reporter-owned fact or artifact is missing.

Post:

```markdown
> *Generated by an AI agent during issue triage.*

## Triage Evidence

**Established:**
- concise fact

**Still needed from the reporter:**
- one specific, actionable request
```

Apply `needs-info`, remove other workflow state labels, and stop. Resume only after the issue thread receives the requested information.

#### `needs-decision`

Use when evidence exposes a genuine product, domain, architecture, security, cost, or scope decision.

Post:

```markdown
> *Generated by an AI agent during issue triage.*

## Triage Evidence

**Established:**
- concise fact

**Decision required:**
- one decision question, with the recommended answer and essential trade-off
```

Apply `needs-decision`, remove other workflow state labels, and stop. Ask one decision at a time. Do not continue by answering for the human.

#### `wontfix`

Use only when evidence shows the report is invalid, duplicate, already implemented, or conflicts with an explicit maintained decision.

Post the evidence and recommendation, apply `wontfix`, and remove other workflow state labels. In this first version, do not close the issue automatically.

#### `ready-to-implement`

Use only when all are true:

- current and desired behavior are clear;
- the claim is sufficiently verified for its risk and uncertainty;
- no reporter information or human decision remains;
- acceptance criteria are independently verifiable;
- validation expectations are known;
- scope and non-goals are explicit;
- the issue fits one fresh implementation context.

The triage workflow may transition autonomously when these conditions are met. Post one consolidated comment containing evidence followed by the authoritative Agent Brief:

```markdown
> *Generated by an AI agent during issue triage.*

## Triage Evidence

**Verification:** confirmed / static evidence only / other precise status

- concise evidence
- validation seam
- residual uncertainty, if any

## Agent Brief

**Category:** bug / enhancement
**Summary:** one-line outcome

**Current behavior:**
Describe the observed status quo.

**Desired behavior:**
Describe the externally observable result, including meaningful edge cases.

**Acceptance criteria:**
- [ ] Specific, independently verifiable criterion

**Validation expectations:**
- Behavioral seam or regression signal
- Repository-required deterministic checks

**Out of scope:**
- Adjacent behavior that must not change

**Open risks:**
- Remaining bounded uncertainty, or `None known`
```

Prefer behavior and stable interfaces over file paths in the Agent Brief. File paths may appear in the evidence section when they substantiate the investigation.

Apply `ready-to-implement` and remove other workflow state labels.

### 7. Handle work that is too large

If the outcome is understood but does not fit one implementation context:

- do not apply `ready-to-implement`;
- do not create child issues in this first skill version;
- post consolidated evidence explaining that implementation decomposition is required;
- leave the issue in `needs-triage`;
- report this as a deliberate pilot limitation for the future `slice-issue` workflow.

Do not mislabel decomposition as `needs-decision` unless a human-owned decision actually blocks the decomposition.

### 8. Report completion

Return a concise local summary:

- issue and resulting state;
- evidence level achieved;
- GitHub comments/labels changed;
- whether HITL is required;
- whether an Agent Brief was published;
- blockers, unsupported decomposition, or residual uncertainty.

Do not offer to implement the issue as part of this skill.
