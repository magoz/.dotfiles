# Report Issue

Capture one observed problem and continue it through triage.

Explicit invocation:

```text
/skill:report-issue <report or current-context reference> [--blocks <issue-number-or-url>]
```

`--blocks 4` means the newly reported issue blocks Issue #4, not the reverse.

## Initial scope

This first version:

- supports one GitHub repository through `gh`;
- runs from a local clone of that repository;
- captures one problem per invocation;
- accepts one optional blocked issue in the same repository;
- creates a minimal report rather than a finished implementation contract;
- continues through the existing `triage-issue` procedure;
- stops after triage and never implements the issue.

## Hard boundaries

Never:

- combine unrelated problems into one issue;
- create a duplicate when an existing issue clearly represents the same problem;
- invent reproduction, impact, user intent, acceptance criteria, or a proposed fix;
- include secrets, tokens, credentials, personal data, environment values, or unnecessary raw logs;
- edit project/source files;
- create a branch or worktree;
- assign an issue;
- commit, push, open a pull request, or merge;
- implement either the new issue or the issue it blocks;
- let a read-only investigator mutate GitHub;
- create tracker labels, Projects, milestones, or broad workflow scaffolding.

The parent Pi session is the sole GitHub mutator. Issue reporting is an intake write, not an execution claim.

## Provenance

Every newly created issue body begins with:

```markdown
> *Generated by an AI agent during issue reporting.*
```

Any intake comment added to an existing issue uses the same provenance line.

Triage comments use the distinct provenance required by `triage-issue`.

## Process

### 1. Resolve the report and repository

- Require either an explicit report or enough current-session evidence to identify one observed problem.
- Confirm the current working directory is a local clone of the target GitHub repository.
- Resolve the canonical `owner/repository`, default branch, and remote.
- If repository identity is ambiguous or the report belongs elsewhere, stop rather than guessing or creating in another repository.
- If `--blocks` is present, resolve exactly one open issue in the same repository and confirm it is an issue rather than a pull request.

Normalize the report into facts:

- observable failure or missing behavior;
- where and when it was observed;
- exact safe reproduction command or user flow, if known;
- concise error or symptom;
- whether it was reproduced on the clean default branch;
- discovery context, such as another issue or draft PR;
- what remains unknown.

Distinguish direct observation, repository evidence, and inference. Never upgrade an inference into a reproduced fact.

### 2. Preflight the tracker

Before creating anything:

- verify GitHub authentication and issue write access;
- verify `needs-triage`, `needs-info`, `needs-decision`, `ready-to-implement`, and `wontfix` exist;
- verify the relevant category label exists when category is already clear;
- verify the optional blocked issue is open and in the same repository;
- read repository issue templates or contribution guidance when present.

This skill does not create missing labels. Stop with the exact setup blocker before issue creation when the canonical triage vocabulary is incomplete.

### 3. Search for duplicates

Search open and closed issues using:

- distinctive error text;
- affected behavior or test name;
- relevant component or subsystem;
- synonyms from the report;
- links to the originating issue or PR when relevant.

Inspect plausible candidates in full, including their comments and current state.

Outcomes:

- **Clear open duplicate:** do not create another issue. Add a concise intake comment only when the new evidence is materially useful, then use that existing issue for the remaining workflow.
- **Clear closed duplicate:** report the prior resolution. Reopen or create a follow-up only when the current evidence proves recurrence or a materially different scope; otherwise stop.
- **Possible but ambiguous duplicate:** stop with the candidates rather than creating noise or making a product decision.
- **No duplicate:** continue to issue creation.

When reusing an existing issue, never overwrite its body or labels before reading its current triage/implementation state. Do not re-triage assigned or actively implemented work unless the user explicitly requested it.

### 4. Create the minimal case file

Choose a concise outcome-neutral title that describes the observed problem, not a speculative solution.

Use this body shape, omitting sections that have no established facts:

```markdown
> *Generated by an AI agent during issue reporting.*

## Report

Concise observable problem.

## Evidence

- `command or user flow` — observed result
- exact concise error or symptom
- clean-default-branch reproduction status

## Context

- Discovered while working on #<issue> / PR #<pr>, when applicable
- Relevant environment or scope without secrets

## Expected invariant

The behavior or repository guarantee currently being violated, when already established.

## Unknowns

- Facts triage still needs to establish
```

Do not add an `## Agent Brief`, implementation checklist, file-by-file plan, or speculative root cause during intake.

Apply:

- `needs-triage`;
- `bug` when an established behavior, test, or repository guarantee is failing;
- `enhancement` when the report requests new behavior;
- no category label when the category is genuinely unclear.

Preserve the issue URL and number returned by GitHub. Re-read the created issue to verify its title, body, labels, state, and repository.

### 5. Record blocker intent without creating a premature edge

When `--blocks` is present, include the originating issue/PR in the new issue's Context section, but do not create the native dependency before triage confirms the report represents a real delivery gate.

The optional target remains unchanged during intake.

### 6. Continue through canonical triage

Before entering triage, preserve this wrapper's continuation state:

- reported or reused issue number;
- optional `--blocks` target;
- whether the native dependency still needs verification.

Read the complete sibling skill:

```text
../triage-issue/SKILL.md
```

Treat it as the canonical procedure; do not duplicate or improvise a second triage implementation here.

Run that procedure against the new or reused issue in the same coordinator session, including:

- repository-guidance inspection;
- proportionate read-only investigation;
- one consolidated triage comment;
- exactly one resulting workflow state;
- an authoritative Agent Brief only when readiness requirements are met.

A terminal outcome from `triage-issue` ends the **triage stage**, not this wrapper. After any triage outcome, resume this skill at Step 7 using the preserved continuation state. The triage instruction to stop means do not implement or continue triage; it does not permit skipping a requested dependency evaluation.

If the triage skill is unavailable or triage cannot safely complete, leave a newly created issue at `needs-triage`, report the exact blocker, and stop. Do not delete the issue.

Do not continue into `implement-issue`.

### 7. Establish the blocker relationship after triage

This is a mandatory post-triage continuation when `--blocks` was requested. The wrapper is not complete until the edge is verified or a precise failure is reported.

Skip relationship mutation only when no `--blocks` target was supplied.

Create a blocker edge when triage evidence confirms that the reported issue is a real unresolved delivery gate for the target issue. The reported issue may itself be `needs-info`, `needs-decision`, `needs-triage` because decomposition is required, or `ready-to-implement`; readiness and blocking are separate concepts.

Do not create the edge when the report is invalid, `wontfix`, already resolved, merely related, or an uncertain possible duplicate. If triage resolves to an existing duplicate, link the verified canonical issue instead.

For GitHub native dependencies:

1. Re-read both issues and verify they are in the same repository.
2. Fetch the blocker's numeric database `id`, not its issue number or GraphQL `node_id`.
3. Check that the dependency edge does not already exist.
4. Add the blocker to the target issue:

```bash
blocker_id=$(gh api repos/<owner>/<repo>/issues/<blocker-number> --jq .id)
gh api --method POST \
  repos/<owner>/<repo>/issues/<blocked-number>/dependencies/blocked_by \
  -F issue_id="$blocker_id"
```

5. Re-read the dependency endpoint or `issue_dependencies_summary` and verify the edge.

If native dependencies are unavailable, use a `Blocked by: #<number>` line only when the repository already maintains that fallback convention. Otherwise leave both issue bodies intact and report that the requested machine-readable relationship could not be established.

Never reverse the edge. With `--blocks 4`, the endpoint path contains Issue #4 and `issue_id` is the reported blocker's database id.

### 8. Report completion

Before reporting success, enforce this completion invariant:

- without `--blocks`, triage reached a valid terminal state;
- with `--blocks`, triage reached a valid terminal state **and** Step 7 either verified the intended edge or recorded an explicit reason the edge must not/could not be created.

Never report the wrapper complete merely because the nested triage stage completed.

Return:

- whether a new issue was created or an existing issue reused;
- issue URL and resulting triage state;
- evidence captured at intake;
- triage evidence level and whether an Agent Brief was published;
- labels/comments changed;
- optional blocker target and verification status;
- any HITL request, duplicate, unresolved relationship, or residual uncertainty;
- explicit statement that no assignment, implementation, branch, or PR action occurred.

## Failure and recovery

- **Preflight failure:** create nothing; report the exact blocker.
- **Creation failure:** do not retry blindly; determine whether GitHub created the issue before retrying.
- **Created but triage failed:** preserve the issue at `needs-triage` and report how to resume.
- **Triage completed but dependency failed:** preserve both issue states, report the exact API failure, and do not fake the relationship in prose unless the repository already uses that fallback.
- **Existing duplicate found:** prefer the canonical issue; do not create or cross-link redundant case files.
